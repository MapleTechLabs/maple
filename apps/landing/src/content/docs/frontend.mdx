Frontend tracing records what happens in the browser before a request reaches your backend. Each click becomes one trace: a span for the navigation, spans for the data it loads, the `fetch` and XHR requests those make, and your backend's spans behind them. With server rendering, the first page load also joins the server render's trace.

The guides below set this up per framework with [`@maple-dev/browser`](/docs/session-replay/browser-sdk) 0.14.0 or later. Here's one navigation where every API call is fast and the page is still slow:

## Choose your framework

Each guide installs the SDK, connects browser traces to your backend, and wires navigations, data loading and errors into the framework's own hooks. React Router and TanStack Router use the adapters in `@maple-dev/browser/react`. The other frameworks call three SDK methods from their router's hooks: `startNavigation`, `traced` and `endNavigation`.

## What you get

- **Navigation spans.** `pageload` for the first route, `navigate` for each one after it, named after the route template (`navigate /projects/:id`). The concrete path is the `url.path` attribute. A navigation cut short by another click ends with `maple.navigation.interrupted: true`.
- **Data-loading spans.** Loaders, `load` functions or resolvers under the navigation, with their requests under them.
- **Backend spans in the same trace.** Requests carry a W3C `traceparent` header: same-origin automatically, cross-origin for the URLs you list in `tracing.propagateTraceHeaderCorsUrls`.
- **Caught errors.** Errors the framework's error boundaries catch are reported once, next to uncaught errors, on the [Errors](/docs/errors/overview) page.
- **Server render joined.** The `pageload` span becomes a child of the server's span when the HTML response carries a `Server-Timing: traceparent;desc="…"` entry or a `<meta name="traceparent">` tag. The server needs OpenTelemetry to write either; each guide shows where.
- **Session replay.** Every span carries the session id, so a trace links to the [recording](/docs/session-replay/replays).

## Limits

- **No async context in the browser.** Inside `traced`, only requests started before the first `await` nest under its span. Start independent requests together with `Promise.all`, or capture `context.active()` from `@opentelemetry/api` before the `await` and run the later request in `context.with(ctx, …)`.
- **Cross-origin APIs must allow the header.** Add `traceparent` to `Access-Control-Allow-Headers` in the API's CORS preflight, or the browser blocks the request.
- **Clock skew.** Browser and server clocks differ, so a server span can appear to start before the `fetch` that caused it. Durations are exact; offsets between browser and server spans are approximate.
- **Cached HTML joins a stale trace.** Don't send the server trace context on responses a CDN or the back/forward cache serves to more than one page load.
