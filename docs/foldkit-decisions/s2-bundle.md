# S2: Can Maple ship as one Foldkit program without route splitting?

Status: decided 2026-10-17. Foldkit 0.168. Measured on main at 2247b5973f.

## Question

A Foldkit program composes Model, update and view statically, so every page ships in the
initial bundle. Only code behind a dynamic `import()` inside a Mount or Command can split. This
spike measures what that costs Maple's web app and what can be done about it.

## Method

All numbers are gzip of the JS in the static import graph of `index.html` (the same walk as
`apps/web/perf/check-bundle-budget.ts`), from production `vite build` output.

1. Baseline: the current build.
2. No splitting: `autoCodeSplitting: false` in the TanStack Router plugin, and a throwaway Vite
   plugin that rewrites every app-level `import("x")` in `apps/web/src`, `packages/ui/src` and
   `packages/widgets/src` into a hoisted static `import * as`. 26 dynamic imports were made
   static (chat panel, command palette, chart registry, tool renderers, alert chart and others).
   Kept lazy: elkjs, the three.js service-map view and the rrweb replay loader.
3. Foldkit approximation: the same build with the Mount-bound libraries and the dev-only lab
   marked `external` (three, @react-three, mermaid, katex, streamdown, shiki, rrweb, @xyflow,
   elkjs, cytoscape, marked, dialkit, `src/lab/`), then also the React-only libraries Foldkit
   replaces (react, react-dom, @base-ui/react, @tanstack/react-*, router-core, clerk-react,
   framer-motion, react-resizable-panels, react-day-picker, @shadcn/react, atom-react).
   Externals drop their transitive dependencies, so this measures what remains for real.
4. Attribution: a sourcemap build, generated bytes per source mapped to a package or directory,
   scaled to each chunk's gzip size.

## Mitigations

(a) Heavy libraries in Mounts. Mandatory and already assumed. It removes about 1000 KB of the
no-splitting bundle (including the lab, which must also be excluded from production through an
`import.meta.env.DEV` guard in the route table instead of today's `beforeLoad` 404). Mount
boundaries should also take the app code that only drives those libraries, such as
`components/service-map/three` (28 KB), the replay engine and the markdown renderer.

(b) Embedding. Each area becomes its own `makeElement` program in its own chunk, started by
`Runtime.embed` from a Mount in a shell app. This can bring startup back to roughly today's
size (shell estimate 700 to 800 KB: contract, effect, layout, icons, ui primitives). The cost is
architectural: separate Models and runtimes per area, shared state (org, auth, time range,
region) passed through Flags and Schema-encoded Ports, the shell owns routing, leaving an area
disposes its runtime and its state, and DevTools and Scene tests see one area at a time. It
rebuilds route splitting by hand at a coarse grain and gives up the single Model.

(c) Lazy view registry. Feasible on the current runtime: `update` and `view` are plain
functions and the program config takes only `Model` as a Schema, not Message. The root Model
Schema and the page Message types stay eager (small); a Command does `import("./pages/x")`,
stores the page's `update` and `view` in a module-level registry and emits `LoadedPage`; the
Model records which pages are loaded and the root delegates through the registry. Savings are
similar to (b) while keeping one Model. The cost is impurity: view and update read state outside
the Model, so replay, DevTools time travel and Scene tests must preload modules, and every page
needs a loading state. This is the design work the Foldkit docs say route splitting would take.

(d) Accept the bigger bundle. Transfer at 1.5 MB gzip versus 703 KB: 4G at 9 Mbps 1.3 s versus
0.6 s, Lighthouse slow 4G 7.5 s versus 3.5 s, desktop at 50 Mbps 0.24 s versus 0.11 s. Parse
and compile goes from 2.3 MB to about 5 MB raw; expect roughly 100 to 200 ms more on a fast
desktop and several times that on a mid-range phone, plus eager evaluation of every page's
module-level Schemas. `apps/web/perf` has no cold-load or TTI measurement to compare against;
its specs measure render behavior, so the first step is to add one. A single chunk also means
every deploy invalidates the whole 1.5 MB; static vendor and area chunks (manual chunking of
static code) keep cache hits across deploys without changing what startup loads. Hazel's
Foldkit app ended at 987 KB; Maple would be about 1.5 times that.

## Recommendation

Go, with conditions. Ship one Foldkit program and accept a startup bundle of about 1.5 MB gzip
(budget 1.6 MB), because Maple is a signed-in, desktop-first dashboard where repeat visits hit
the cache and the extra cost is about 0.7 s of transfer on 4G and well under 0.3 s on desktop.
Conditions: (1) every heavy library listed above lives behind a Mount or Command `import()`,
enforced by a startup-graph check like today's `forbiddenStartupPatterns`; (2) the lab is
compiled out of production; (3) static code is manually chunked for cache stability; (4) a
cold-load TTI test is added before the first page moves, on the React app, so the Foldkit app
is measured against it. If that test shows the single bundle regressing TTI beyond what the
team accepts, adopt (c), the lazy view registry, for the largest areas (infra, dashboard
builder, agent sessions, settings, integrations). Embedding (b) is not recommended for page
areas; reserve it for genuinely independent widgets.
